# OBS 33 and what it changes for Sponsifer, November 2026

This note assesses every change in OBS Studio 33.0.0 and 33.0.1, and in obs-websocket 5.7.5 and 5.7.6, against what Sponsifer does. It covers the overlay and the dock (browser pages inside OBS), the on-air logger, `status`, `setup` and the report, all of which reach OBS over its WebSocket. Every claim is marked as verified against a source, verified on a real OBS, or still to test. It follows [obs-extensibility-2026-09.md](obs-extensibility-2026-09.md), which was written against OBS 32.

Sponsifer was built and first run against OBS 32.2.2 with obs-websocket 5.7.4. On 2026-11-02 this machine runs **OBS 33.0.1 with obs-websocket 5.7.6**, the newest release of both. obs-websocket ships inside OBS; its own GitHub releases stopped at 5.0.1, and its tags continue.

## The verdict

OBS 33 breaks nothing Sponsifer depends on, and two things in the code were brought up to date with it.

- **Safe Mode.** OBS 33 no longer starts the WebSocket server in Safe Mode, so the "OBS is not answering" message now says so.
- **The program scene's name.** `currentProgramSceneName` is deprecated. `setup` and `status` now read the current field, `sceneName`, and fall back to the old one for older servers.

The largest change, Chromium 127 to 150 inside browser sources and docks, has been checked by eye on a real OBS 33.0.1. What is left is an interval actually on air, which no session has yet produced.

## The protocol Sponsifer speaks, checked against 5.7.6

Everything listed here was verified against [protocol.md at 5.7.6](https://github.com/obsproject/obs-websocket/blob/5.7.6/docs/generated/protocol.md), and on the real OBS where noted.

- **Requests and events.** Every request and event the code sends or reads still exists:
  - requests: `GetVersion`, `GetInputList`, `GetInputSettings`, `GetSourceActive`, `GetStreamStatus`, `GetCurrentProgramScene`, `GetVideoSettings`, `GetCanvasList`, `CreateInput`, `SetInputSettings`;
  - events: `StreamStateChanged`, `InputActiveStateChanged`, `InputShowStateChanged`, `CurrentProgramSceneChanged`, `CurrentPreviewSceneChanged`, `SceneItemEnableStateChanged`, `StudioModeStateChanged`.
- **Response fields.** The fields read from those requests are unchanged.
- **Subscription bits.** The high-volume input bits are still `1 << 17` and `1 << 18`, and still outside "All".
- **The one deprecation.** `GetCurrentProgramScene` marks `currentProgramSceneName` and `currentProgramSceneUuid` deprecated, "slated to have the `currentProgram`-prefixed fields removed from in an upcoming RPC version". It now answers `sceneName` and `sceneUuid` too. The real OBS 33.0.1 sends both. Sponsifer identifies at RPC version 1, so nothing breaks until it negotiates a later one, but `obs.program_scene()` reads `sceneName` now.
- **No protocol changes in 5.7.5 or 5.7.6.** The commits are Safe Mode, CI, docs and translations.

## The canvas question

Twitch's Dual Format streams a second, vertical canvas beside the main one. Sponsifer's log has a single-canvas limit, which the README states.

**What OBS 33 offers.** obs-websocket 5.7.6 can list canvases (`GetCanvasList`, since 5.7.0), announce them (`CanvasCreated`, `CanvasRemoved`, `CanvasNameChanged`), and take an optional `canvasUuid` on scene and source requests. But:

- **`GetSourceActive` cannot be asked about one canvas.** Its `canvasUuid` only resolves a source's name; `videoActive` is still "whether the source is showing in Program", for the process as a whole.
- **A non-main canvas has no program scene in the protocol.** `GetSceneList` returns `null` for one, and `GetCurrentProgramScene` says "Canvases do not have any concept of a program or preview scene".
- **libobs's new `obs_canvas_video_active()` is not exposed** by the WebSocket.

So **OBS 33 does not lift the limit.** No request can say on which canvas a source was on air.

**What could be built.** The WebSocket can say which canvases' scenes *contain* a source: `GetSceneList` for each canvas, then each scene's items, recursing into nested scenes and groups. Recorded in the session line and shown by `status`, that would let a report say more. If no canvas but the main one uses a placement, the minutes can only be the main feed's. If another canvas uses it too, the ambiguity is real, and the report says so as it does now.

**The limits of that check, unverified:**
- Whether a plugin's private canvas appears in `GetCanvasList` at all. "Only emit core signal handlers for public canvases" suggests private canvases exist. If they are not listed, the check can only say "no *listed* canvas but the main one uses it".
- How Twitch's Dual Format creates its vertical canvas on a given setup.
- This machine runs one canvas (`GetCanvasList` returns one), so nothing about a second canvas can be checked here; it could only be tested against a stand-in OBS.

**Recommendation: record this, and build it when a real dual-format streamer, or a second canvas to test against, exists.** The session line already records the canvas count, so every log written today says whether a second canvas was running. This is Sam's call after this assessment. The Horizons report's caution holds: proof machinery before a sponsor has seen a report.

## Verified on this machine, 2026-11-02 (OBS 33.0.1, obs-websocket 5.7.6, not streaming)

- **`status`** read every source and flagged a "Sponsor overlay" aimed at a port where nothing answers.
- **`setup`**, pressed with Sam's agreement for test deal dl-901, re-pointed that source and made the three missing ones, hidden, in the scene on screen. `status` then showed all four at the app's address, with the server answering.
- **A label log** wrote its session line (one canvas) and a clean end. Its lock refused the app's Start, and a label log of a sponsor's source was refused.
- **`GetCurrentProgramScene`** returns `sceneName` beside the deprecated field.
- **Screenshots of the hidden sponsor sources** through `GetSourceScreenshot` came back fully transparent. All four reported `videoShowing: false`, and a browser source that is not showing is not painted (obs-browser marks its browser hidden to Chromium). So those frames say nothing about rendering, and the rendering check needs the sources shown.

- **The placements and the dock in OBS 33's Chromium 150**, shown by Sam: reported good.

## Still to test

- **An interval on air.** On air means the stream output is live and the source is in the program feed. The logger reads `GetStreamStatus`, never `GetRecordStatus`, so **recording a scene produces no on-air time**, by design. To test without broadcasting:
  - **A local RTMP server.** Point OBS's stream at, for example, `rtmp://127.0.0.1/live` served by a local server such as MediaMTX. Nothing leaves the machine, and the stream output is genuinely active. This needs a server installed, which is Sam's call.
  - **Twitch's bandwidth test.** Append `?bandwidthtest=true` to the stream key, or tick "Enable Bandwidth Test Mode" when logged in to Twitch in OBS. This sends a real stream to Twitch's ingest without going live. One OBS forum user reported going live anyway, so watch the Twitch dashboard during the first try. Sources: [OBS forum, test mode going live](https://obsproject.com/forum/threads/stream-going-live-despite-bandwidth-test-mode-enabled.176189/), [OBS forum, bandwidth test while logged in](https://obsproject.com/forum/threads/twitch-bandwidth-test-while-being-logged-in.104254/).
- **A nested scene or group**, open since September; OBS 33's fix to groups in Studio Mode makes it worth running.
